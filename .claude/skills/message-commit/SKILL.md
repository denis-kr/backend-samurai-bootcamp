# Message Commit

Generates a clear, conventional commit message from the real `git diff` of uncommitted changes, then offers to commit.

## Workflow

1. **Check repo state first.**

   ```bash
   git status --short
   git rev-parse --abbrev-ref HEAD
   ```

   If there are no changes at all (staged or unstaged), tell the user there's nothing to commit and stop.

2. **Get the diff to summarize.**
   - If there are staged changes (`git diff --cached --stat` is non-empty), summarize the staged diff — that's what will actually be committed:
     ```bash
     git diff --cached
     ```
   - If nothing is staged but there are unstaged changes, summarize those instead, and mention in your reply that nothing is staged yet:
     ```bash
     git diff
     ```
   - If both staged and unstaged changes exist and they look unrelated, say so and ask (or reasonably assume) whether to cover just staged, or everything — default to staged, since that's what `git commit` would record.
   - Also check for untracked new files (`git status --short` shows `??`) — a diff won't show their content. List them by name and, if small, `cat` them to understand what they add.

3. **Read the actual diff, don't skim the file list.** Look at real hunks to understand _what changed and why_, not just which files touched. Pay attention to:
   - Whether it's a fix, new feature, refactor, docs, test, chore, perf, or revert.
   - The most significant change if there are several — lead with that.
   - Anything that looks like a breaking change (removed/renamed public functions, changed signatures, changed config keys).

4. **Write the commit message.**
   - **Subject line:** imperative mood ("Add", "Fix", "Refactor" — not "Added"/"Fixes"), ≤ 50 chars where reasonable (hard cap ~72), no trailing period.
   - Use a Conventional Commits prefix (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`, `perf:`, `style:`, `build:`, `ci:`) **only if the repo already uses that convention** — check recent history first:
     ```bash
     git log --oneline -15
     ```
     If the existing log doesn't use prefixes, don't invent the convention — just write a plain imperative subject.
   - **Body (only if the change needs explaining):** blank line after subject, then wrapped prose or bullet points covering _what_ changed and _why_, not a line-by-line narration of the diff. Skip the body entirely for small, self-explanatory changes — don't pad it.
   - Never mention "generated by Claude" or add tool signatures unless the user's own commit history does that.

5. **Present the message, then offer to commit — don't commit unprompted.**
   Show the drafted message in a fenced block. Ask (or, if the user's original request already implied committing, e.g. "commit these changes", proceed directly) before running:
   ```bash
   git commit -m "<subject>" -m "<body>"
   ```
   If nothing is staged and the user wants to commit everything shown in the unstaged diff, stage it first (`git add -A` or the specific files) and confirm what was staged before committing.

## Notes

- If the diff is large or spans unrelated concerns (e.g. a feature plus an unrelated formatting pass), say so and suggest splitting into multiple commits rather than forcing one message to cover everything.
- If `git diff` output is too large to read in full, use `git diff --stat` first to get an overview, then read the hunks for the most substantial files.
- Match the terseness/verbosity of the user's existing commit history — some projects want one-liners only, others want detailed bodies.
